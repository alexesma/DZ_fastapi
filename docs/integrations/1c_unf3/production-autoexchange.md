# Проверка и включение автообмена DragonZap ↔ 1С:УНФ

Инструкция относится к штатной синхронизации УНФ через универсальный формат
**EnterpriseData** и FTP. Адрес `/api/1c/exchange` с логином
`ONE_C_EXCHANGE_LOGIN` — другой, старый канал «Обмен с сайтом». Он не включает
EnterpriseData и не должен одновременно передавать те же заказы.

## 1. Обновить сервер

Перед обновлением сделайте резервную копию базы и сохраните файлы `.env`.
Далее используйте обычный процесс развёртывания проекта. Если развёртывание
выполняется вручную:

```bash
cd /root/DZ_fastapi
git pull --ff-only
cd infra/dev
docker compose -f docker-compose.yaml -f docker-compose.prod.yaml pull
docker compose -f docker-compose.yaml -f docker-compose.prod.yaml \
  up -d --force-recreate web scheduler frontend ftp
```

Проверить результат:

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}' | \
  grep -E 'dz_(fastapi|scheduler|frontend|ftp|db)'
docker exec dz_fastapi poetry run alembic current
docker exec dz_fastapi test -d /app/onec_exchange
docker exec dz_scheduler test -d /app/onec_exchange
```

Контейнеры `dz_fastapi`, `dz_scheduler` и `dz_ftp` должны использовать один
том `onec_exchange`. Не удаляйте этот том и файлы сообщений при обновлении.

## 2. Проверить параметры сервера

В `/root/DZ_fastapi/.env` должны быть заданы:

```env
ONE_C_EXCHANGE_DIR=/app/onec_exchange
ONE_C_PHYSICAL_WAREHOUSE_NAME=Основной склад
ONE_C_PHYSICAL_WAREHOUSE_GUID=<GUID существующего физического склада УНФ>
ONE_C_ED_HANDSHAKE_POLL_SECONDS=60
ONE_C_ED_RECEIVING=Документ.РеализацияТоваровУслуг,Документ.ПоступлениеТоваровУслуг,Документ.ЗаказКлиента,Документ.ЗаказПоставщику,Документ.ВозвратТоваровОтПокупателя,Документ.ВозвратТоваровПоставщику,Документ.ОприходованиеТоваров,Документ.СписаниеТоваров
```

`ONE_C_ED_RECEIVING` означает, что DragonZap принимает обратно номера и
признаки проведения **своих** документов. Самостоятельно созданные в УНФ
документы не проводят движения в DragonZap: они попадают в журнал для ручной
проверки.

FTP-реквизиты находятся отдельно в `/root/DZ_fastapi/infra/dev/.env`:

```env
FTP_USER=onec
FTP_PASSWORD=<действующий пароль FTP>
FTP_PUBLIC_HOST=dragonzap.online
FTP_PORT=2121
```

После изменения любой переменной пересоздайте `web`, `scheduler` и при
изменении FTP-реквизитов — `ftp`. Обычного `docker restart` недостаточно.

Проверить состояние протокола без изменения данных:

```bash
docker exec dz_fastapi python -c '
from dz_fastapi.services.one_c_enterprise_data import get_enterprise_data_status
import json
print(json.dumps(get_enterprise_data_status(), ensure_ascii=False, indent=2, default=str))
'
```

В результате должны быть каталог обмена, коды двух узлов, номера сообщений и
непустой список согласованных типов `negotiated_sending` после первого обмена
с УНФ.

## 3. Настроить сценарий в УНФ

Откройте существующую настройку **DragonZap — Синхронизация данных через
универсальный формат**.

Параметры FTP:

| Поле | Значение |
|---|---|
| Сервер | `dragonzap.online` |
| Порт | `2121` |
| Пользователь | `onec` |
| Пароль | пароль из `FTP_PASSWORD` |
| Пассивное соединение | включено |
| Архивировать сообщения | включено |
| Пароль архива | пусто |

В правилах отправки УНФ → DragonZap:

1. Нормативно-справочную информацию можно поставить **«Не отправлять»** —
   хозяином карточек остаётся DragonZap.
2. Для документов выберите **«Отправлять, начиная с даты»** и дату начала
   пилота.
3. Если УНФ позволяет выбрать виды, отметьте реализации, поступления, заказы,
   оба возврата, оприходования и списания. Они нужны только для возврата
   номера, GUID и результата проведения наших документов.
4. Если выбор видов недоступен, временно разрешите все документы с даты
   пилота. Посторонние документы будут видны в журнале DragonZap, но их нужно
   разбирать вручную.
5. Сохраните настройку и один раз выполните синхронизацию вручную.

После ручного запуска откройте в DragonZap:

**Документы → Обмен с 1С** (`/documents/1c`).

Должны выполняться условия:

- «Каталог обмена» — доступен;
- «Ожидает чтения УНФ» — нет после завершённого цикла;
- список «Согласованы типы на отправку» содержит тип, который планируется
  включить;
- счётчик подтверждённого сообщения увеличивается после следующего запуска
  УНФ;
- нет предупреждения, что обмен остановился.

## 4. Безопасный ручной пилот

Пока оставьте автоотправку выключенной.

1. Создайте и проведите в DragonZap одно небольшое тестовое поступление.
   Укажите поставщика, договор УНФ, склад, товар, количество и цену.
2. На странице «Обмен с 1С» найдите его событие и отправьте вручную либо
   нажмите «Отправить следующую партию сейчас» после временного включения
   только поступлений.
3. Запустите синхронизацию в УНФ вручную.
4. Проверьте в УНФ контрагента, договор, товар, физический склад, количество,
   цену, НДС и проведение документа.
5. Запустите синхронизацию УНФ второй раз. Этот цикл должен вернуть в
   DragonZap GUID, номер и признак проведения.
6. В DragonZap убедитесь, что событие имеет два разных результата:
   **«Прочитано УНФ»** и **«Проведено в УНФ»**. Первое не заменяет второе.
7. Только после появления остатка в УНФ проведите тестовую реализацию. Иначе
   УНФ создаст расходную накладную, но не проведёт её из-за недостатка.
8. Для маркированной позиции проверьте два разных КИ: принять A и B, отгрузить
   B, вернуть B. В возврате и УКД должен остаться именно B; в EnterpriseData
   возврата он должен находиться в `МаркировкиУпаковок`.

Если пилот создал второй склад, не продолжайте: исправьте
`ONE_C_PHYSICAL_WAREHOUSE_GUID`, пересоздайте контейнеры и повторите тест.

## 5. Включить автоматическую отправку

На странице **Документы → Обмен с 1С**:

1. Выберите старт **«Только новые»**. Не выбирайте «Вся история», пока аудит
   истории не показывает нулевые разрывы и не согласованы начальные остатки.
2. Размер партии установите **1**. После нескольких успешных дней можно
   увеличить до 5; начинать с 50 не нужно.
3. Сначала отметьте только **«Поступления»** и нажмите
   **«Включить выбранный обмен»**.
4. Проведите новое поступление и дождитесь двух циклов УНФ. Проверьте чтение и
   проведение.
5. Добавьте **«Реализации»** и повторите тест на новом документе.
6. После успешных поступления и реализации добавьте **«Возвраты»**.
7. «Складские корректировки» включайте только когда интерфейс показывает,
   что УНФ согласовала оприходование и списание. Если списание не согласовано,
   переключатель останется недоступным.
8. Заказы клиентов и поставщикам включайте последними. До этого отключите
   передачу тех же заказов через старый «Обмен с сайтом», иначе возможны дубли.

В УНФ включите расписание существующего сценария после ручного пилота.
Рекомендуемый стартовый интервал — **15 минут**. Планировщик DragonZap
проверяет каталог каждую минуту, поэтому нормальная задержка полного цикла —
до двух интервалов УНФ.

## 6. Ежедневный контроль первых дней

Проверяйте на странице обмена:

- очередь не стоит дольше 30 минут;
- нет события с ошибкой подготовки;
- нет неподтверждённого сообщения старше двух запусков УНФ;
- прочитанные документы получили номер и результат проведения УНФ;
- в журнале посторонних документов нет необъяснённых записей;
- количество и стоимость поступлений, реализаций и возвратов совпадают;
- по маркированному товару совпадает конкретный КИ, а не только количество.

Логи на сервере:

```bash
docker logs dz_scheduler --since 2h 2>&1 | \
  grep -E 'EnterpriseData|one_c_enterprise|UNF'
docker logs dz_ftp --since 2h 2>&1 | tail -100
```

## 7. Если обмен остановился

1. На странице «Обмен с 1С» нажмите **«Остановить автоотправку»**. Уже
   отправленный файл не удаляйте.
2. Не обнуляйте номера сообщений и не удаляйте
   `.dz_enterprise_data_state.json`.
3. Проверьте работу FTP, расписание УНФ, список согласованных типов и текст
   ошибки конкретного события.
4. После исправления используйте **«Повторить после исправления»**, а не
   создавайте копию документа.
5. Если документ ошибочный и передавать его нельзя, поместите только его
   событие в карантин с причиной.
6. Включайте обмен снова в режиме **«Продолжить»**, чтобы сохранить прежнюю
   границу событий.

Для маркированного возврата поставщику DragonZap намеренно не создаёт
собственный УКД: корректировочный документ должен выпустить исходный продавец.
Такой возврат не следует обходить ручной подменой XML.
