# Диадок: что уже используем и что осталось (аудит на 2026-11-01)

Источники: документация Контура (раздел «ЭТрН» developer.kontur.ru/doc/diadoc-api/logistic/waybill/*)
и код проекта. Полный справочник HTTP-методов с сайта автоматически выгрузить не удалось
(страницы рендерятся скриптом), поэтому по общим методам список составлен по коду
и известной структуре API — перед реализацией каждый метод сверять со справочником.

## Уже применено (dz_fastapi/http/diadoc_client.py)
GetMyUser, GetMyOrganizations/GetOrganization, GetDocumentTypes, GetCounteragents,
GetDocuments (V3, polling), GetDocument, GetEntityContent (V4), PostMessage, PostMessagePatch,
GenerateTitleXml, GenerateReceiptXml, GenerateSignatureRejectionXml,
GenerateRevocationRequestXml, печатная форма, облачная подпись (CloudSign + SMS),
OAuth. Статусы исходящих обновляются регламентом; для перевозочных документов
читается внешний документооборот ГИС ЭПД (`KlMt`) — только чтение статуса.

## Не применено (по убыванию пользы)
1. **Лента событий вместо опроса списка** — GetNewEvents / GetDocflowEvents (V5), GetDocflows (V5).
   Сейчас входящие и статусы получаем опросом GetDocuments: нет событий «подписан контрагентом»,
   «отказ», «аннулирование запрошено», «ошибка роуминга», недоставка (DeliveryFailureNotification).
2. **Статус входящих документов** (подписан ли нами/контрагентом, запрос уточнения,
   аннулирование) — берётся из документооборота; в интерфейсе входящих его нет.
3. **Запрос уточнения (RequestAmendment) / отказ в подписи с причиной** — отказ есть,
   «запрос уточнения» (например, при расхождении суммы с письмом) нет.
4. **Машиночитаемые доверенности (МЧД)** — PowerOfAttorney*: нужны, если подписывает не
   руководитель; ошибки валидации приходят сущностью PowerOfAttorneyStatus.
5. **Шаблоны, черновики, отложенная отправка** — PostTemplate, TransformTemplateToMessage,
   IsDraft/SendDraft/RecycleDraft, DelaySend (нужны для ЭТрН и для «подготовить УПД, подписать позже»).
6. **Комментарии и резолюции** (согласование внутри компании), перемещение между подразделениями.
7. **Проверка контрагента** до отправки (наличие ящика, GetOrganizationsByInnList/ Acquire…) и
   приглашение контрагента.
8. **Webhook-подписка** (если доступна по тарифу) вместо периодического опроса.

## ЭТрН через Диадок
Документация: TypeNamedId = `LogisticsWaybill`, Version `kl_trn_mt_05_01`,
Function: reception (Т1/Т2), delivery (Т3/Т4), cost (Т5/Т6), readdress (Т7), relay (Т8), fwd.
Связка перевозки — `mt-id` (УИД_ТрН) и `kl-id` (= MessageId титула Т1); Т3/Т4 приходят
отдельным сообщением (fwd), группировать их нужно по УИД, а не по MessageId.
Статус ГИС ЭПД — сущность OuterDocflow `KlMt`; подтверждение водителя — `KlDriverConfirm`;
стадия — тег `kl-status` (обновляется только на Т1/Т2).

**Найденное расхождение:** `dz_fastapi/services/diadoc_transport.py` распознаёт ЭТрН по
`RoadTransportWaybill`, а по документации тип называется `LogisticsWaybill`. Если в реальных
данных приходит `LogisticsWaybill`, статусы перевозок сейчас не отображаются. Нужно добавить
значение в `TRANSPORT_TYPE_NAMED_IDS` и сверить на реальном документе из прода.

План интеграции (зависит от роли компании в перевозке):
- Грузополучатель (Т3): читать входящие Т1/Т2 событиями, показывать перевозку и УИД, формировать и
  подписывать Т3 (приёмка полная/частичная/отказ) через GenerateTitleXml + CloudSign.
- Грузоотправитель (Т1): создавать Т1 из отгрузки (PostMessage или шаблон), подписывать, отслеживать
  Т2/Т4 и статус в ГИС ЭПД.
- Везде: лента событий по ящику с фильтром по TypeNamedId, привязка титулов по ParentEntityId,
  обработка отказов и ошибок OuterDocflow (Status.Type = Error).
Сейчас подписание титулов ЭТрН ведётся в 1С.

## Честный знак
Уже есть: учёт кодов маркировки (КИЗ из УПД, привязка по GTIN, нормализация), вход в ГИС МТ
через облачную подпись Диадока, проверка статусов кодов (`check_marking_codes_with_gis`),
вывод из оборота документом (`start_gis_mt_withdraw_task`).
Не сделано (кандидаты): автоматическая сверка кодов входящего УПД со статусами ГИС МТ при приёмке,
передача кодов в исходящие УПД покупателю, приёмка/отгрузка в схеме с УПД-«прослеживаемость»
через ГИС МТ (документы приёмки/отгрузки), возвраты кодов, отчёты о расхождениях.
