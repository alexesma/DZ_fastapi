# Обмен DragonZap, 1С:УНФ, Диадока и «Честного знака»

Аудит от 18 ноября 2026 года. Проверена рабочая копия на основе `71b8c78`, включая локальные изменения. Цель — оптовая закупка и продажа автотоваров с учётом конкретных экземпляров. Розница через кассу, производство, импорт и вывод для собственных нужд требуют отдельных сценариев, если компания выполняет такие операции. Настройки действующей базы Рарус, рабочего ящика Диадока и личного кабинета ГИС МТ в рамках аудита не проверялись.

## Что можно доказать

На локальной тестовой базе запущены наборы `test_one_c*`, `test_diadoc*`, `test_*marking*` и `test_gis_mt*`. Прошли 280 тестов за 119,74 секунды, pytest сообщил об одном предупреждении. Этот прогон проверяет реализацию и моделируемые ответы интеграций. Обмен с действующими внешними системами в него не входил.

Предоставленный октябрьский XML УНФ содержит сообщение № 4 с одним оприходованием НФНФ-000001 и количеством 2, поле ReceivedNo равно 0. Это подлинный пример состава сообщения УНФ → DragonZap. Состояние сегодняшней очереди из него определить нельзя. В журнале проекта отдельно зафиксирован более поздний тест, в котором УНФ создала расходную накладную, а проведение упёрлось в остатки.

## Приоритет исправлений

| Приоритет | Наблюдение и последствие | Что реализовать и как принять |
|---|---|---|
| До массовой маркированной продажи | В обработке статусов Диадока есть внешний оборот перевозочных документов. Специализированная обработка `TtGis` для маркировки не обнаружена. Оператор может сообщить ошибку уже после подписи | Хранить последний статус и историю с идентификаторами сообщения и сущности, ссылкой на квитанцию и деталями ошибок. Различать обработку, фиксацию отгрузки, переход покупателю и отмену фиксации. Проверить повтор и запоздалое событие |
| До массовой маркированной продажи | Вывод из оборота ставит код в состояние `WITHDRAWN` сразу после получения ID созданного документа. Последующее отклонение может остаться незамеченным | Состояние ожидания, опрос результата по ID, обработка отказа и восстановление после сбоя. Код с неопределённым результатом недоступен повторной отгрузке |
| До массовой маркированной продажи | Фактический скан поддерживается. Настройка автоматического заполнения недостающих кодов по партиям имеет значение по умолчанию true. Неверный экземпляр может попасть в формально правильное количество. В проверке состояния реестра отсутствующая запись не попадает в ветку ошибки состояния | Для поэкземплярного учёта требовать точное множество сканов, регистрацию каждого кода и принадлежность конкретной отгрузке. Отдельно проверить старые партии, частичную сборку и две параллельные отгрузки |
| До массовой маркированной продажи | Без активного токена или при недоступности ГИС МТ проверка перед черновиком может пропустить отправку. При подписи черновик берётся из сохранённого файла. После подготовки документа его состояние могло измениться | Ввести явное состояние «проверка отложена», правило допуска по товарной группе, контроль версии документа и набора кодов перед подписью. Одинаковый контроль для одного документа и пакета |
| До массовой приёмки | При проведении коды регистрируются из строки поступления. Экран приёмки отдельно хранит ожидаемые и физически подтверждённые коды. Факт проведения сам по себе не доказывает совместного совпадения поштучных кодов | Для выбранных маркируемых групп связать проведение, расхождения и титул покупателя с результатом сканирования. При 4 ожидаемых и 3 фактических кодах оператор может оформить расхождение, но не безусловную приёмку четырёх |
| До возвратов с маркировкой | Возврат от клиента выбирает первые N кодов отгруженной строки по ID. Возврат поставщику аналогично выбирает коды партий. При частичном возврате можно вернуть в учёт другой экземпляр. Уменьшение поступления с кодами при корректировке явно отправляется на ручную обработку | Сканировать конкретный экземпляр, связывать его с исходной строкой и документом ЭДО. Поддержать реально используемые ставки и особые операции. Для неподдерживаемого варианта заранее показывать понятную причину |

## Ход исправлений — вывод из оборота

В рабочей копии после подтверждения по SMS DragonZap закрепляет выбранные коды за заявлением. На странице «Маркировка» можно увидеть номер заявления, ID в ГИС МТ и результат проверки. При активном токене планировщик каждые три минуты проверяет до 25 ожидающих заявлений, начиная с тех, которые дольше всего ждали проверки.

После `CHECKED_OK` в истории каждого кода появляется движение вывода из оборота. При окончательном отказе код возвращается в своё предыдущее состояние. Если связь прервалась до получения ID, нужно найти исходное заявление по номеру в личном кабинете «Честного знака», ввести его ID в журнале маркировки и нажать «Проверить». DragonZap сверит содержимое с подписанным заявлением. Если документ найти не удалось, коды остаются заняты до разбора отправки.

Для внедрения требуются миграция `da180ce6f4b1` и обновление приложения, планировщика и интерфейса. Для заявлений, завершённых до обновления, нужна отдельная сверка. Описание статусов и метода получения документа приведено в [документации True API ГИС МТ](https://docs.crpt.ru/gismt/True_API/).

## Как внедрять

1. **Зафиксировать старт.** На рабочем узле сохранить версии приложений, состав отправки и приёма, расписания, последние пакеты и возраст очереди, GUID физического склада, выбранную организацию и рабочий ящик, источник нумерации, состояние токена и режим автоматического назначения кодов. Снять остатки на одну дату. Сверить старый прайс, DragonZap и УНФ по одной физической позиции. Сверить фактически имеющиеся маркированные экземпляры отдельно.
2. **Назначить владельцев.** Предлагаемый вариант — DragonZap отвечает за заказ, сборку, фактический код и создание реализации, УНФ за проведение в своей учётной базе, Диадок за подписанный оригинал и документооборот, ГИС МТ за итог операции с маркировкой. Для каждого сценария выбрать одного отправителя юридического документа. Для движений из УНФ определить перечень разрешённых типов и порядок принятия самостоятельного документа. Учитывать доступность штатных правил УНФ без расширений.
3. **Проверить обычный товар.** Один приход, одна частичная отгрузка, повторная доставка того же сообщения и проверка проведения. Начальные остатки переносить отдельной согласованной операцией. Коммерческий остаток из прайса не заменяет партию, цену прихода и движения склада.
4. **Пройти маркированный оптовый пилот.** Использовать разрешённый тестовый контур либо реальную согласованную поставку. Подобрать два экземпляра одного товара с различимыми кодами A и B. Принять оба, отгрузить B, вернуть B. Сохранить документ и GUID УНФ, идентификаторы УПД и обеих сторон, статусы ГИС МТ и движение именно B. Отправке юридически значимого тестового документа предшествует согласование участников.
5. **Пройти отрицательные сценарии.** Подмена A на B, чужой владелец, истёкший токен, скан дважды, продажа одного экземпляра двумя кладовщиками, частичная приёмка, УКД на конкретный код, аннулирование, перезапуск после подписи или принятия пакета. У каждого случая ожидается явная остановка либо документированное восстановление, без двойного списания, подписи и УПД.
6. **Включать пооперационно.** После прохождения пилота — расписание для проверенных видов. Ежедневно сверять количество, стоимость, статусы проведения и коды. Отдельно выводить «ожидает подписи», «прочитано УНФ», «УНФ отказала в проведении», «ошибка ГИС МТ» и «нет окончательной квитанции». У каждой ошибки должен быть ответственный и повтор, сохраняющий идентичность операции.

Критерий приёмки для оптовой реализации — по конкретному КИ можно восстановить физическую приёмку и сборку, исходную и возвратную строки, номера документов DragonZap и УНФ, подписанный УПД и результат ГИС МТ. По итогам сверки нет необъяснённых расхождений количества, суммы и владельца кода. Для обычного товара ветка ГИС МТ не применяется.

Для протокола 1С значение ReceivedNo подтверждает приём сообщения. [Описание EnterpriseData у 1С](https://v8.1c.ru/tekhnologii/obmen-dannymi-i-integratsiya/standarty-i-formaty/format-enterprisedata/)

Диадок документирует заполнение маркированного УПД, результаты обработки, фиксации и отмены, а также получение квитанций. [Маркированные документы в API Диадока](https://developer.kontur.ru/doc/diadoc-api/instructions/documents/marking.html)

Применимость правил к каталогу нужно устанавливать по товарной группе и конкретному товару. [Разъяснение «Честного знака» по ассортименту моторных масел](https://markirovka.ru/knowledge/tovarnye-gruppy/motornye-masla/kakie-motornye-masla-podlezhat-obyazatelnoy-markirovke)
